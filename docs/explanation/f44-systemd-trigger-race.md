# F44 systemd-trigger race during package upgrades

## The trap

A `dnf` transaction on a Fedora 44 host that updates a library carrying a `%triggerin --` or `%triggerpostun --` scriptlet shipped from the `systemd` spec, in the same transaction as a systemd update that triggers a `systemctl daemon-reexec`, hits a structural timing race. The trigger scriptlet body invokes `systemctl` or `systemd-run` against PID 1's DBus listening socket; the concurrent reexec briefly removes that socket; the trigger call lands in the gap and fails.

The failed call surfaces in the transaction's stderr/stdout as one of two canonical strings, `Failed to start transient service unit: Remote peer disconnected` or `Failed to start jobs: Transport endpoint is not connected`. The `dnf` transaction continues to completion regardless. Subsequent `systemctl` or `systemd-run` invocations issued by later scriptlets in the same transaction — those that fall outside the reexec window — succeed cleanly and leave normal `type=SERVICE_START … res=success` records in the journal.

## Why it happens

PID 1 owns the system DBus listening socket and the private control socket at `/run/systemd/private`, and a `systemctl daemon-reexec` re-executes PID 1 in place: the running binary closes the listening sockets, the new binary opens them, and any client `connect(2)` issued during the gap fails with the canonical `ECONNRESET`/`ENOTCONN` pair that `systemctl` and `systemd-run` render as `Failed to start transient service unit: Remote peer disconnected` or `Failed to start jobs: Transport endpoint is not connected`. The kernel boundary is the listening socket's lifecycle: while the old binary's `close(2)` of the socket is followed almost immediately by the new binary's `bind(2)`/`listen(2)` reopen, the few hundred milliseconds of socket absence are long enough for any concurrently scheduled trigger scriptlet to issue its client `connect(2)` against the missing endpoint and observe the absence as the canonical EOF/connect error pair. A trigger scriptlet that uses only `daemon-reload` rather than `daemon-reexec` does not surface the trap, because a reload re-reads PID 1's configuration without closing the listening socket. The race is structural and surfaces for any library whose `%triggerin --` or `%triggerpostun --` scriptlet is co-bumped in the same transaction as a systemd `daemon-reexec`; the trigger scriptlet's purpose is service-non-critical state refresh, which is why the failed call's effect on the host is bounded and why the dnf transaction reaches completion regardless.

The class is therefore deterministic for the co-bumped-transaction case rather than a flaky environmental artefact. An observer who walks two consecutive `dnf` invocations on the same host, splitting the systemd update from the affected library update across the two transactions, sees neither failure string. The race window is a function of PID 1's reexec duration alone — not of host load, init-scope topology, or scheduler pressure — so the trap reproduces deterministically on any F44 host that schedules the two updates in one transaction and disappears deterministically when the operator splits them across two.

## How to detect it

Four signals together identify the trap class unambiguously: a `journalctl --since=<dnf-window-start>` invocation shows `Reload requested`, `Reloading`, `Reloaded`, and `Reexecuting` lines within the same second-window as the operator-visible failure string; the audit channel returns no `type=AVC` for any boot-time domain transition; the audit channel returns no `type=SECCOMP` for any privilege-drop pipeline; the audit channel returns no `type=SERVICE_START` record with `res=failed` for the affected trigger; and the unit-status surface (`systemctl status <unit>` for any unit whose drop-in or pre-deploy was suspected as the root cause) reads `active (running)` with no error counter advance. The reexec-line bracket is the positive signal that a reexec window did occur during the dnf transaction; the three audit-channel emptinesses and the active unit-status are the negative signals that no real defect class is involved.

```text
<dnf-window-start>  systemd[1]: Reload requested from client PID 1, by 'reload-or-restart-units'.
<dnf-window-start>  systemd[1]: Reloading...
<dnf-window-start>  systemd[1]: Reloaded.
<dnf-window-start>  <lib>.scriptlet[<pid-of-systemd-run>]: Failed to start transient service unit: Remote peer disconnected
<dnf-window-start>  <lib>.scriptlet[<pid-of-systemd-run>]: Failed to start jobs: Transport endpoint is not connected
<dnf-window-start>  systemd[1]: Reexecuting.
<dnf-window-start>  systemd[1]: Started <unit>.
```

The transcript above is synthetic. The two failure lines are bracketed by the `Reload requested` line that opens the systemd-shipped trigger scriptlet's reload-or-reexec sequence and the `Reexecuting` line that closes it; both failure lines are produced by the `systemctl`/`systemd-run` client invoked from inside the trigger scriptlet, not by PID 1 itself. The trailing `Started <unit>` line confirms that PID 1's listener is back online and serving subsequent requests in the same transaction.

## How to mitigate it

The trap is an upgrade-time race between two unrelated systemd lifecycle events; it is not a hardening regression and does not warrant rolling back any unit drop-in, `SystemCallFilter=` carve-out, `NoNewPrivileges=yes` directive, namespace-restriction directive, or custom SELinux policy module. The bounded post-trap operator action set is: confirm via `journalctl --since=<dnf-window-start>` that a `Reexecuting` line falls within the same second-window as the failure string; for any trigger whose action is genuinely state-critical — atypical for the systemd-shipped trigger scriptlet family, which is by convention a cache or preset refresh — invoke `systemctl status <unit>` to verify the post-trigger state of the relevant unit; and, if the state-refresh has been missed, rerun the underlying state-refresh command manually outside an active reexec window after the dnf transaction completes. None of these actions modifies host configuration.

```bash
journalctl --since="<dnf-window-start>" --until="<dnf-window-end>" \
  | grep -E '(Reload requested|Reloading|Reloaded|Reexecuting|Failed to start)'
```

The discrimination signal against the three load-bearing real-defect classes documented in this tree is the simultaneous absence of three audit footprints during a confirmed reexec window: no `type=AVC` for any boot-time domain transition, no `type=SECCOMP` for any privilege-drop pipeline, and no `status=226/NAMESPACE` for any `ReadWritePaths=` setup; if any of the three is present the failure belongs to that class and is investigated as a real defect. A `type=AVC` record points to a missing `nnp_transition` allow rule and a likely boot-time failure on the next reboot. A `type=SECCOMP` record points to a privilege-drop syscall denied by a positive `SystemCallFilter=` carve-out and a unit-level `failed (signal)` state. A `status=226/NAMESPACE` exit on a unit whose drop-in lists `ReadWritePaths=` points to a runtime bind-mount race against a path that does not yet exist on a fresh `/run/` tmpfs. None of those three footprints is consistent with the trap class described here, and a confirmed reexec window with all three absent is the operator-facing closure of the discrimination.

The class is an upgrade-time artefact of how RPM transaction sequencing intersects PID 1's reexec lifecycle: it is not a hardening property, not a hardening defect, and not a security-relevant signal in either direction, and it must not be folded into the host's hardening narrative on either side. An automated post-update reviewer that greps the dnf log on substrings such as `Failed`, `disconnected`, or `not connected` reports a regression that is not real; the alarming substring shape of the canonical pair of error strings is the artefact's most operator-visible feature, and a reviewer that escalates the report into a hardening rollback inflicts measurable damage on the host's posture for no defensible benefit. Manual operator review reads the timestamp of the failure string against the reexec lines in `journalctl` and the audit-channel emptinesses before treating any such report as actionable, and ignores the trap class entirely once the discrimination signal has been confirmed.

Edge cases the mitigation does not cover:

- A trigger scriptlet whose action is genuinely state-critical (atypical for the `%triggerin --`/`%triggerpostun --` family, which is by convention used for cache and preset refresh): the failed call leaves the post-trigger state un-refreshed for the duration of the upgrade. The mitigation is to invoke the underlying state-refresh command manually outside an active reexec window, after the dnf transaction completes. The Pattern does not enumerate which triggers are genuinely state-critical — that is a per-package operator-policy concern.
- A host with multiple back-to-back systemd reexecs in the same transaction (rare; happens when the systemd update itself triggers a follow-on reload of a daemon that links systemd's libraries): the affected trigger window may extend over several seconds rather than the typical few hundred milliseconds. The detection signal still holds — `journalctl` shows multiple `Reexecuting` lines bracketing the failure timestamp — but the operator's manual-rerun window must wait for the last `Reexecuting` line, not the first.
- An automated post-update reviewer that grep's the dnf log on substrings `Failed`, `disconnected`, or `not connected`: the reviewer reports a regression that is not real. The mitigation is on the reviewer side, not on the host: the reviewer either combines its substring grep with a `journalctl --since=<dnf-window>` reexec-line check, or it whitelists the canonical pair of error strings on the basis of an identified reexec window. The Pattern does not prescribe a specific automation surface; the boundary it draws is that no host-side configuration change is appropriate.
- A dnf-transaction order in which the systemd update and the affected library update are scheduled in different transactions (typical of operators who run `dnf update systemd && dnf update <other>` in sequence): the trap does not surface, and the operator's confirmation that no reexec window overlaps the trigger is automatic. The Pattern does not require this transaction-splitting as the mitigation; the canonical mitigation is the classification rule (B2), and transaction splitting is a side-effect of operator habit, not a recommended hardening procedure.
