# The rpm-soname dependency-check trap

## The trap

An operator assessing whether a package is removable from the local system runs `rpm -q --whatrequires <pkg>` against the candidate and reads the result as a single line. When the command prints `no package requires <pkg>` (or returns the empty set with exit code `1`), the operator interprets the result as a confident negative answer: no installed package depends on the candidate, therefore the candidate is unused, therefore removal is safe. The query is fast, the output is unambiguous in shape, and the operator carries forward an authoritative-feeling verdict that the candidate has no reverse-dependents.

The next step exposes the trap. A subsequent `dnf remove <pkg>` either refuses outright with a hard-dependency error that names an installed package the rpm-side query did not surface, or commits a transaction that pulls in a much larger set of removals than the single-package change the operator intended. In either case, the rpm-side empty result was a misleading signal that the operator could not have known to mistrust from the empty result itself — there is no warning, no diagnostic, no exit-code distinction that flags the answer as incomplete; the trap is silent at the rpm-query boundary, and the only evidence of its presence is the divergence visible at the depsolver step.

## Why it happens

`rpm -q --whatrequires <pkg>` queries the local rpmdb's `Requires` table for entries whose dependency string equals the package name, and that table does not index SONAME capabilities of the form `libfoo.so.N()(64bit)`, versioned symbol provides, file-path provides, virtual provides declared via `Provides:`, or rich and Boolean dependencies declared via `Requires:` with `(...)` syntax. The query reads one table and returns one kind of edge — the package-name reverse-edge — and any dependency formulated in any other shape passes through the query without contributing to the result set. The query is therefore not wrong; it is complete only for the narrow class of dependencies the table indexes, and the empty set it returns means "no installed package declares a name-based `Requires:` against this candidate", not "no installed package depends on this candidate".

When a candidate package exports one or more shared-object SONAMEs and its installed dependents declare their dependency against the SONAME capability rather than against the providing package's name, `rpm -q --whatrequires <pkg>` returns the empty set even though the candidate is load-bearing for one or more dependents, and only the reverse-lookup form `rpm -q --whatrequires 'libfoo.so.N()(64bit)'` — with the parentheses and bit-width tag preserved verbatim and the entire capability string single-quoted to protect it from shell expansion — surfaces the actual dependents. The same shape of false-empty-result arises when an installed dependent declares its dependency against a virtual `Provides:` the candidate emits, against a file path the candidate ships, or against a Boolean dependency expression that the rpmdb's flat `Requires` table does not index — in each case `rpm -q --whatrequires <pkg>` returns the empty set while `dnf repoquery --installed --whatrequires <pkg>` returns one or more installed reverse-dependents, because the dnf-side query runs a resolver pass against the full provides graph rather than reading a single rpmdb table. A third variant arises when the candidate is a transitive dependency of a top-level metapackage: the candidate's direct reverse-dependent set may be short and unambiguous, but each direct dependent is itself a hard dependency of a more visible package higher up the chain, and the chain is invisible to a single `--whatrequires` invocation against the candidate because each chain step is a separate package-name edge that the operator must walk explicitly or else trust the depsolver to walk on the operator's behalf.

A boundary marker separates the trap-bearing family of tools from the trap-free family: a query that bypasses the depsolver inherits the rpmdb-table-incompleteness trap, a query that drives the depsolver does not. The same trap class applies to any tool that consults only the rpmdb's `Requires` table — ad-hoc scripts that parse `rpm -qR <pkg>`, that filter `rpm -qa --requires`, or that walk the rpmdb directly via `rpm --qf '%{REQUIRENAME}'` — because none of those forms walks the full provides graph either; tools that drive the depsolver (`dnf`, `dnf5`, `microdnf`, the libdnf API) do not share the trap, because they consult the full provides/requires graph including virtual provides, file-path provides, and Boolean dependencies.

## How to detect it

The authoritative answer to "is this candidate removable?" is a four-layer check, not a single query. Layer one runs `rpm -q --whatrequires <pkg>` for the basic package-name reverse-edge — fast, useful as a first filter, accepted as final only when no further layer adds anything. Layer two enumerates the candidate's exported SONAMEs with `rpm -q --provides <pkg> | grep '\.so\.'` and, for each SONAME, runs `rpm -q --whatrequires 'libfoo.so.N()(64bit)'` to surface the SONAME-side reverse-dependents the package-name query misses. Layer three runs `dnf repoquery --installed --whatrequires <pkg>` to resolve virtual provides, file-path provides, and Boolean dependencies that the rpm-side query does not index. Layer four runs `dnf remove --assumeno <pkg>` as the depsolver-side end-test, which prints the transaction the resolver would actually commit — including any cascade through intermediate packages and any hard-dependency error that would block the removal — without committing it.

```text
$ rpm -q --whatrequires <pkg-a>
no package requires <pkg-a>
$ rpm -q --provides <pkg-a> | grep '\.so\.'
libfoo.so.N()(64bit)
$ rpm -q --whatrequires 'libfoo.so.N()(64bit)'
<pkg-b>-1.2.3-1.fc44.x86_64
$ dnf repoquery --installed --whatrequires <pkg-a>
<pkg-b>-0:1.2.3-1.fc44.x86_64
$ dnf remove --assumeno <pkg-a>
Dependencies resolved.
Error:
 Problem: The operation would result in removing the following protected packages: <pkg-b>
Operation aborted.
```

## How to mitigate it

`dnf remove --assumeno <pkg>` is the authoritative end-test because it is the same resolver path that a real `dnf remove <pkg>` would take, run with the commit step suppressed by the `--assumeno` flag's automatic "no" response to the final confirmation prompt; the transaction summary it prints is the depsolver's real verdict against the current installed set, not an estimate or a heuristic. Any difference between the transaction summary and what the operator expects — a hard-dependency error against an installed package the operator did not realize was a reverse-dependent, a removal cascade through intermediate packages the operator did not realize were on the chain, a clean single-package removal where the operator expected a cascade — is a difference the operator must reconcile before re-invoking the command without the `--assumeno` flag.

Treat `rpm -q --whatrequires <pkg>` as a pre-filter only, never as an authoritative removability verdict; the combination of the SONAME reverse-lookup, `dnf repoquery --installed --whatrequires <pkg>`, and `dnf remove --assumeno <pkg>` is the authoritative answer set, and bypassing any of the three risks either a failed transaction or a removal cascade that takes out packages the operator did not intend to lose. For a removal that crosses any package the operator did not personally install in the current shell session, the four-layer check is mandatory; for a removal limited to a package the operator installed by name in the same session and has not yet referenced from anything else, the four-layer check remains the safer default, because intermediate package-tooling operations between install and remove can introduce dependents the operator did not author.

This Pattern documents a query-semantic trap, not a removability heuristic — whether any given package should be removed is a per-host decision that depends on the installed service set, the desktop or server profile, and the operator's hardening goals, and the Pattern only ensures the dependency picture is complete before that decision is taken. The Pattern does not prescribe which packages to remove, does not endorse a removal-by-default posture, and does not offer a list of safe-to-remove packages: each of those would be host-specific and would defeat the trap-class statement.

Edge cases the mitigation does not cover:

- A candidate package that is currently uninstalled but listed in a comp-group, environment-group, or module the operator has selected: `dnf remove --assumeno <pkg>` is not relevant (the package is not installed), but the next `dnf install` of the group brings the candidate back in. The four-layer detection sequence does not address group- or module-driven re-installation; the operator must additionally run `dnf group info <group>` or `dnf module info <module>` to enumerate the group's package set, and excluding the candidate from a group selection requires a `dnf install --exclude=<pkg>` invocation or an `excludepkgs=` entry in `/etc/dnf/dnf.conf` rather than a removal.
- A package whose SONAMEs are dlopen'd at runtime rather than linked at build time: `rpm -q --provides <pkg>` lists the SONAME, and `rpm -q --whatrequires 'libfoo.so.N()(64bit)'` may return the empty set because the dlopen consumer does not declare a build-time link dependency on the SONAME. The candidate is still load-bearing — the consumer's runtime fails when the SONAME disappears — but neither the rpm-side nor the dnf-side query surfaces the dlopen edge, and the four-layer detection sequence does not catch it. The mitigation in that case is operator knowledge of the consumer's runtime behavior, not a query.
- A package supplied through a third-party repository or a locally-built rpm whose `Requires:` declarations against the candidate are formulated incorrectly (for example, a package-name `Requires:` against a candidate that has been renamed at the upstream level): the rpm-side and dnf-side queries both miss the runtime relationship because the dependency string in the third-party package does not match any installed package's name or provides. The four-layer detection sequence is bounded by the correctness of the installed packages' `Requires:` declarations; it does not protect against a third-party packaging defect.
- A removal that is structurally permitted by the depsolver but breaks an out-of-rpm relationship the operator relies on: a configuration file in `/etc/**` written by the operator that references a binary the candidate ships, a systemd drop-in that calls a script in the candidate's `%files`, an Ansible playbook that assumes the candidate is installed. None of these relationships are visible to the rpm or dnf provides/requires graph, and `dnf remove --assumeno` reports a clean transaction even when the removal will break the operator's own configuration. The four-layer detection sequence covers package-level dependencies only; out-of-rpm relationships are the operator's responsibility to enumerate before the removal.
