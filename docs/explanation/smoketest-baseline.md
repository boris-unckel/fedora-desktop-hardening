# The smoketest-baseline trap

## The trap

An operator deploys a hardening change against a daemon — a unit-level drop-in, a custom SELinux module, a sysctl write — and then runs a functional smoketest associated with that daemon to confirm that the change has not broken the daemon's operating surface. The smoketest exits non-zero, or its output contains a content-level failure line, and the operator concludes that the hardening change is responsible. The conclusion is drawn from a single post-deploy snapshot of the smoketest, taken against the changed host without a paired pre-deploy capture of the same smoketest against the unchanged baseline of the same host. The smoketest's verdict is treated as load-bearing on the basis of one observation, in one direction, against one configuration state.

The reaction path turns the misclassification into a posture loss. Believing the hardening change is the cause, the operator rolls back or widens the just-deployed directive — a removal of a namespace-restriction directive, a relaxation of a `SystemCallFilter=` carve-out, a deletion of a custom SELinux module, an inversion of a `ProtectKernel*=` or `ProtectSystem=` setting, a flip of `NoNewPrivileges=`. The smoketest is re-run and the failure persists, because its root cause was not the hardening change. The operator is left with a degraded hardening posture and an unresolved smoketest failure: the directive that constrained the daemon's attack surface has been backed out, and the symptom that motivated the rollback is still present. Subsequent attempts to restore the directive face the same single-snapshot evidence and the same wrong inference, so the rollback tends to stick.

## Why it happens

A functional smoketest is a black-box probe whose non-zero result space is the union of many independent failure modes — a hardware-class limit at a controller or device, a firmware-class quirk in a peripheral whose advertised capability is not honoured at the protocol level, a stock-software defect in the daemon under test, a transient environmental condition such as an unreachable peer or a busy resource, and a hardening directive that newly restricts a code path the smoketest exercises — and a single post-deploy snapshot cannot decide which member of that union produced the observed failure, because the snapshot does not distinguish a failure the host already exhibited from a failure the deploy introduced. The five categories are mutually independent: a kernel-side rejection rendered as `Operation not supported` or `Invalid argument` against a request the daemon issues to a controller is not on the same causal chain as a `SystemCallFilter=` denial against a syscall the daemon executes in user space, and neither is on the same chain as a stock-software regression in the distribution-shipped binary; the smoketest's single exit code carries one bit of pass-or-fail information and cannot factor across the five.

The trap surfaces across three categories of smoketest, and the third is the most trap-prone. A service-CLI verify-subcommand reports drift between configured and observed state by exit code; a scheduled check-unit's state surface (the exit code reported via `systemctl status <unit>` or the `Result=` field on the unit) is read as a pass/fail signal; an end-to-end exercise touches hardware or peripheral state — a mount-and-read, a probe-and-list, a ping-and-reach — and reports the outcome through the unit's `MainPID` or the wrapper script's exit code. The third category is the most trap-prone because hardware-class and firmware-class failure modes are stable across reboots: a controller that rejects an operation today rejects it tomorrow, regardless of which drop-in was added in between, and the failure presents identically in pre- and post-deploy captures whenever it is the root cause. A snapshot taken only after the deploy cannot tell that shape of failure from a deploy-induced regression — both render the same exit code, on the same line, against the same target — and the third category therefore exhibits the highest base rate of misattributed rollback in the absence of a paired baseline.

## How to detect it

Before the first configuration write of a hardening change that is to be measured by a functional smoketest, the operator invokes the smoketest against the unchanged host and persists the result. The invocation uses the same command, the same arguments, the same output filter, the same locale, the same effective uid, and the same SELinux role that the post-deploy invocation will use, and the resulting stdout, stderr, and exit code are written to a baseline record stored alongside the deploy script. The baseline is the artefact the post-deploy capture is compared against; without it, no later capture is interpretable as either a regression signal or a no-change signal.

After the hardening change is deployed and the system has reached the same steady state the baseline was captured under — typically a reboot when the change is a unit-level drop-in, a service restart when the change is a runtime-applied directive — the smoketest is re-invoked under identical conditions and a content-level diff is computed between the post-deploy record and the baseline record. The diff, not the post-deploy exit code in isolation, is the load-bearing signal: a non-zero post-deploy exit code that is byte-identical to the baseline exit code and output indicates that the failure was already present before the deploy, while a non-zero post-deploy exit code that differs from the baseline indicates a deploy-time change to the smoketest's observable surface. A zero post-deploy exit code against a non-zero baseline is also a diff and is treated as a separate signal — the deploy has changed the smoketest's outcome, in the direction of clearing a pre-existing failure, which is itself worth investigating.

```text
$ <smoketest-command> > <baseline-path>.stdout 2> <baseline-path>.stderr
$ echo "$?" > <baseline-path>.rc
(deploy hardening change)
(reboot)
$ <smoketest-command> > <post-deploy-path>.stdout 2> <post-deploy-path>.stderr
$ echo "$?" > <post-deploy-path>.rc
$ diff <baseline-path>.stdout <post-deploy-path>.stdout
$ diff <baseline-path>.stderr <post-deploy-path>.stderr
$ diff <baseline-path>.rc <post-deploy-path>.rc
```

## How to mitigate it

When the pre-deploy baseline records the same failure shape that the post-deploy invocation reports, the hardening directive is exonerated as the cause; the diagnostic path moves one layer below the hardening surface — to the driver, the firmware, the daemon's stock behaviour, or the environmental condition that produced the failure in both captures — and the hardening directive remains in place. The diagnostic redirect is not optional: the smoketest failure is real, the host is exhibiting it, and the absence of a hardening-side cause does not absolve the lower layer. The hardening posture is preserved because the baseline ruled out the directive; the lower-layer investigation proceeds because the failure shape persists. The two outcomes are independent and both must be completed for the verification to close.

A score-style improvement claim — a unit-test pass, a directive-coverage uplift, a static-analysis count — without a paired functional smoketest is not load-bearing as a hardening claim, and a functional-smoketest failure without a paired pre-deploy baseline is not load-bearing as a hardening regression: both directions of the symmetry require their corroborating anchor before any rollback or rollout decision is taken. The symmetry is the discipline: a deploy that ships a score uplift but never exercises the daemon end-to-end may have left an unobserved functional break in place, and a deploy that ships a smoketest failure but never captured the pre-deploy shape may roll back a directive that was never the cause. Neither direction is safer than the other to leave unanchored; both require their second probe before the operator commits to a posture change.

The baseline record and the post-deploy record are only diff-comparable when they are captured under byte-exact invocation conditions — the same locale, the same output filter pipeline, the same effective uid, and the same SELinux role — because a drift in any of those four dimensions produces diff-noise that hides the real signal and reintroduces the single-snapshot trap one level deeper. A baseline captured under `LANG=en_US.UTF-8` and a post-deploy record captured under a different locale will diff against each other on every line that renders an errno string, regardless of whether the underlying kernel rejection has changed; a baseline that pipes the smoketest through `grep` or `awk` to elide a noisy line and a post-deploy record captured without the same filter will diff on the elided content; a baseline captured as root and a post-deploy record captured as a confined user will diff on every line whose visibility is gated by uid; and a baseline captured from one SELinux role and a post-deploy record captured from a more-privileged role will diff on every line that depends on audit-relevant denials a less-privileged role would not see. Each of those drifts is a single-snapshot trap displaced from the smoketest itself into the baseline-and-post-deploy pair: the diff cannot tell hardening-induced change from invocation-condition drift, and the corroborating anchor the mitigation rests on collapses.

Edge cases the mitigation does not cover:

- A smoketest whose result space is non-deterministic across two invocations of the unchanged host (a probe that races against a peer's response, a check that depends on a network condition that fluctuates within minutes): the baseline-and-diff sequence reports a difference between the two captures even when no hardening change is in flight. The mitigation is to run the baseline several times and accept the smoketest only when its result is stable across the repeats; a probe whose result is not stable cannot be used as a hardening regression signal at all, and the operator either replaces it with a deterministic probe or accepts that the hardening change cannot be measured by this surface.
- A smoketest whose first execution alters the host's state in a way that the second execution depends on (a cache-warming probe, an end-to-end exercise that creates a resource the next invocation reuses): the pre-deploy capture and the post-deploy capture are not symmetric, because the host's state has changed between them. The mitigation is either to reset the affected state between the two captures or to use a smoketest that is idempotent at the host-state level; the Pattern's diff discipline assumes the smoketest does not carry hidden state forward.
- A hardening change whose effect on the smoketest is only visible after a long-running soak (a directive that constrains behaviour observed only under sustained load, an SELinux denial that fires only on a rarely-exercised code path): the immediate post-deploy capture matches the baseline because the affected code path has not been exercised yet. The Pattern's discipline closes the deploy-time decision boundary; it does not address regression that surfaces only at steady state, which is a separate monitoring concern with separate tooling.
- A baseline captured under conditions that the operator believes are byte-exact but in fact differ on a dimension the byte-exact-comparability sentence does not list (the time-of-day a probe runs against a peer with diurnal load, the order in which a multi-call probe issues its sub-calls when ordering is not specified): the diff surfaces a difference that the operator cannot trace to any of the four documented dimensions. The mitigation is to enumerate the smoketest's hidden inputs as part of the baseline metadata (not only the command line) and to either pin them or capture them in the record so a later operator can decide whether a diff reflects a hardening change or a hidden-input drift.

- [The rpm-soname dependency-check trap](./rpm-soname-dependency-check.md) — Both Patterns are silent-collapse traps in which a single authoritative-feeling query yields a verdict that the operator must not act on without a corroborating second probe: `rpm -q --whatrequires <pkg>` collapses "no installed package depends on this candidate" and "the dependent set is non-empty but not formulated as a package-name edge" into one empty result, and a post-deploy smoketest collapses two failure provenances into one observation; in both cases the load-bearing artefact is the structured probe sequence — the four-layer dependency check for the removability case, the pre-deploy-then-post-deploy baseline-and-diff sequence for the smoketest case — and not the headline tool's single output.
