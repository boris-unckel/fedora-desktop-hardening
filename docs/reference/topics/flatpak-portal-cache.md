# Flatpak document-portal cache lifecycle

> **Prerequisite.** This topic assumes the Foundation layer has been applied. See [Bootstrap](../../tutorials/bootstrap-hardened-host.md).

## Scope

This topic documents the runtime-cache-lifecycle reflex an operator applies around any sandbox-tightening `flatpak override` operation against a Flatpak application: the per-user `xdg-document-portal.service` holds file-access tokens in two storage classes (persistent and transient), and these tokens survive the upstream override push that tightens the application's static sandbox manifest. Without an explicit cache flush, files that the application was previously authorized to read through the freedesktop Document portal remain readable through the FUSE-mounted token paths under `/run/user/${uid}/doc/` for the lifetime of the portal-service process — even though the application's freshly-merged sandbox manifest now denies the host paths the tokens point to. The deliverable is a procedural reflex (one user-bus `systemctl --user restart` call) plus a verify discipline anchored on the FUSE filesystem (the authoritative cache-state truth anchor, in contrast to the partial view exposed by `flatpak documents list`). The Topic applies on hosts where the operator login is mapped to the confined SELinux user `staff_u` and the sandbox-tightening override is issued from the role-switched `sysadm_t` admin context against the system-wide override store at `/var/lib/flatpak/overrides/<appid>`.

This topic does **not** cover the `flatpak override` permission model itself (the syntax of `--filesystem=`, `--socket=`, `--device=` flags; the `[Context]` section format of override-store files; the precedence rules between system-wide and per-user override stores; the merge semantics with the application's static manifest), the freedesktop Document portal D-Bus interface (`org.freedesktop.portal.Documents`, `org.freedesktop.portal.OpenFile`) at the method-set level, the OCI access-token semantics, the `xdg-desktop-portal-flatpak` proxy backend, the per-Flatpak-application sandbox-permission posture (which permissions a given application declares by default, which permissions an operator commonly tightens — owned by application-specific Topic articles), the `staff_u`-mapping deployment decision (owned by the Foundation layer), Flatpak-side workarounds (for example `flatpak override --reset`, log-out and log-back-in to drop the user-systemd state, or `pkill` against the portal-service — the canonical operator-facing reset path is the named user-systemd `restart` invocation documented here), the implementation differences between `xdg-desktop-portal-gtk` and `xdg-desktop-portal-gnome` (the cache-lifecycle behaviour is identical across both backends because the cache lives in the frontend `xdg-document-portal` component), the reverse direction of sandbox loosening via `flatpak override` (a loosening operation does not require a cache flush — fresh tokens issued under the loosened sandbox are inherently a superset of the prior set), and freedesktop portal interactions other than the Document portal (`org.freedesktop.portal.FileChooser`, `org.freedesktop.portal.Background`, `org.freedesktop.portal.Camera`) — those have their own cache-lifecycle properties that may or may not exhibit the same reflex requirement, and this topic confines itself to the Document portal because that is the surface the cache-lifecycle reflex reliably applies to. The `systemd-analyze security` numeric score model is also out of scope: this topic ships no system-side service unit and the score model does not apply.

## End-state configuration

The end-state ships **no** operator-installed file. There is no systemd unit, no systemd drop-in, no `/etc/profile.d/` script, no configuration file under `/etc/flatpak/`, no polkit rule, no sudoers fragment, no desktop-entry override, no SELinux CIL module, no `semanage fcontext` mapping, no `restorecon` invocation, and no file-label change. The end-state is a procedural reflex wrapped around any upstream sandbox-tightening `flatpak override` operation — namely the explicit user-bus restart of the per-user `xdg-document-portal.service` — combined with a verify discipline that uses the per-user FUSE filesystem under `/run/user/${uid}/doc/by-app/` as the authoritative truth anchor for token presence.

### Topic identity

The pipeline under hardening is the cache-lifecycle window that opens immediately after an operator pushes a sandbox-tightening `flatpak override` against a Flatpak application that consumes Document portal access. The runtime artefacts involved are the per-user `xdg-document-portal.service` (a user-systemd unit under the operator's account, providing the freedesktop Document portal interface for Flatpak applications) and the per-user FUSE filesystem the portal-service mounts under `/run/user/${uid}/doc/`. The end-state depends on three stock packages on Fedora 44 or later: `flatpak` (provides `/usr/bin/flatpak` and the per-user portal client integration), `xdg-desktop-portal` (provides the freedesktop portal frontend service set, including the `xdg-document-portal` implementation backend dispatch), and one of `xdg-desktop-portal-gtk` or `xdg-desktop-portal-gnome` (provides a GTK or GNOME backend implementation; either is acceptable, the choice depends on the desktop session the operator runs). The role's preflight asserts the three-package family is present (with the GTK/GNOME backend slot satisfied by either implementation) and aborts fail-fast on a missing `flatpak` or `xdg-desktop-portal` entry. The topic is structurally out of scope on hosts that do not run a graphical desktop session (the per-user `xdg-document-portal.service` is started on demand by graphical-session D-Bus activation and is not normally addressable on a console-only host), and applies to operators whose desktop login is mapped to `staff_u`.

### Topic shape — runtime-cache-lifecycle hygiene

This topic occupies a structurally different shape than the sibling Flatpak topics in this tree, which patch single stock-policy gaps via topic-owned CIL modules at priority 400. The end-state is **not** "a daemon runs in a hardened domain", **not** "a service ships a systemd drop-in", **not** "a custom CIL module is loaded at priority 400", and **not** "a file label is altered". The end-state is a procedural reflex — an explicit user-bus restart of `xdg-document-portal.service` immediately after the operator issues an upstream sandbox-tightening `flatpak override` — combined with a verify discipline anchored on the per-user FUSE filesystem under `/run/user/${uid}/doc/by-app/`. Every downstream subsection is framed by this structural fact: the role's `tasks/main.yml` orders preflight → pre-reset snapshot → reset → post-reset verify; the modify stage is exactly one mutating action (the user-bus `systemctl --user restart`); no system-wide artefact is written to disk; the role's `files/` directory contains exactly the probe and verify scripts plus the role README.

### Token classes

The freedesktop Document portal exposes two file-token storage classes that an operator must distinguish:

- **Persistent tokens** are created when an application calls the portal's `org.freedesktop.portal.Documents.Add()` method with the `persistent` flag, typically because the application wants the user-granted access to survive an application restart. Persistent tokens are recorded in the per-user portal database and are listed by `flatpak documents list`. They survive a portal-service restart only if the application calls `Add()` again on the next launch with the same payload; the post-restart re-list is the operator's signal that the persistent class is also flushed by the restart.
- **Transient tokens** are created when an application uses the portal's `org.freedesktop.portal.OpenFile` interface (the typical desktop file-chooser dialog: the application requests "let the user pick a file", the portal spawns a system-mediated chooser dialog out of process, the user clicks a file, the portal hands the application a token-shaped path that resolves through the FUSE mount). Transient tokens are valid only while the application holds the file handle or the portal-service session is live; they are **not** listed by `flatpak documents list` (the CLI inspects only the persistent-class store).

Both classes materialize on the host as a per-token directory under `/run/user/${uid}/doc/<token>/` (the per-token FUSE bind), and both classes are aggregated by the application-indexed view at `/run/user/${uid}/doc/by-app/<appid>/<token>/`. The FUSE path is therefore the **only** authoritative cache-state anchor; the `flatpak documents list` CLI output is a partial view by design and is not a cache-truth signal. The probe inventory and the verify Soll/Ist comparison both read both signals separately: the persistent count from `flatpak documents list` and the per-application token count from `/run/user/${uid}/doc/by-app/<appid>/`. The two are not redundant — a `flatpak documents list`-based verify alone would miss the transient class entirely.

### Cache lifecycle

When an operator runs an upstream `flatpak override` that tightens the sandbox of a Flatpak application (for example, dropping the `home` filesystem permission or revoking a specific D-Bus permission), the override push has two distinct effect surfaces with two distinct latencies:

- **Static sandbox effect.** The override is persisted to the override store at `/var/lib/flatpak/overrides/<appid>` (system-wide override) or `~/.local/share/flatpak/overrides/<appid>` (per-user override); the next `flatpak run` of the application reads the merged manifest, and bwrap constructs the new sandbox with the tightened bind-mount set. This effect is immediate for new application launches.
- **Cache-lifecycle effect.** File-tokens that the application acquired before the override push remain materialized in the per-user FUSE filesystem under `/run/user/${uid}/doc/by-app/<appid>/`. These tokens were granted by the portal under the prior sandbox posture and continue to resolve to the host paths they were created against until the per-user `xdg-document-portal.service` is restarted. A still-running instance of the application — and any subsequent launch of the application until the portal-service restart — can dereference those token paths and read the host files, even though the application's freshly-merged sandbox manifest no longer mounts the originating host directories.

The override push has tightened the static sandbox without tightening the dynamic portal cache. The reflex this topic ships is the explicit cache flush via `systemctl --user restart xdg-document-portal.service` immediately after the override push; the cache-lifecycle property is a stable end-state property of the freedesktop Document portal architecture as shipped in the Fedora-44 `xdg-desktop-portal` and `flatpak` package families, not an incident-specific observation.

### Reset action

The reset is a single `systemctl` invocation issued against the operator's user-systemd instance:

```bash
systemctl --user restart xdg-document-portal.service
```

The call runs as the operator's own UID against the operator's own user-bus; **no** `sudo`, **no** SELinux role-switch to `sysadm_t`, and **no** root privileges are required for the restart itself. The portal-service is per-user, lives under the operator's user-systemd manager, and is restartable from the operator's own session without escalation. The probe section's read of `/var/lib/flatpak/overrides/<appid>` does require role-switched `sysadm_t` for tree-self-containment, but that is a separate inspection step, not part of the reset action. Post-reset the portal-service re-spawns automatically on the next D-Bus method call from any Flatpak application; the operator does not need to keep an application running across the restart, and the operator does not need to log out and back in. The reset takes effect immediately and atomically — there is no transitional cache state where some tokens are flushed and others are retained.

### File modes

This topic ships **no** operator-installed system-side configuration files. The role writes nothing under `/etc/`, nothing under `/root/`, and nothing under `/var/lib/`. The only artefacts under operator control are the probe and verify scripts shipped under the role's `files/` directory; both retain Ansible-skeleton permissions on the management host and are not copied to the target host as system-wide installations (the role uses them via `ansible.builtin.script` invocations from the management host, executed under `become_user: <operator>`). The operator UMASK 0027 reflex documented elsewhere in the Foundation layer does not apply here, because no `/etc/`-side or `/root/`-side file is written by the role.

## Verification

The role's `files/` directory ships two scripts: a read-only probe that operates partially as the operator and partially with role-switched `sysadm_t` for the override-store read, and a Soll/Ist verify that reports per-application drift attribution. Both scripts run from the operator's user session under the user-bus connection mode and are runnable standalone for out-of-band debugging.

### Probe

```bash
bash ansible/roles/topic_flatpak_portal_cache/files/probe.sh
```

The probe reports state without judging it. It enumerates package presence (`rpm -q flatpak xdg-desktop-portal`), the operator's runtime SELinux mapping via `id -Z` (the canonical applicability anchor — `staff_u:staff_r:staff_t`), the user-systemd state of the portal-service (`systemctl --user status xdg-document-portal.service --no-pager`, reporting active state, last-spawned timestamp, and main PID purely informationally; the liveness signal is captured by `[[ -d /proc/${pid} ]]` against the reported main PID), the persistent-class store count via `flatpak documents list`, the FUSE-anchored full-cache view via `ls -la /run/user/$(id -u)/doc/by-app/` (per-`<appid>` token count under each application subdirectory), the operator-installed Flatpak inventory and per-application permission summary via `flatpak list --app --columns=application,permissions` (informational, used to map any tokens observed under `by-app/<appid>/` back to the application's current sandbox posture), and per-`<appid>` override-store content via `sudo -r sysadm_r -t sysadm_t cat /var/lib/flatpak/overrides/<appid>` for each application that has at least one entry in the system-wide override store. The override-store read uses the role-switched `sudo -r sysadm_r -t sysadm_t` form because plain `sudo` from a `staff_u`-mapped login remains in `staff_sudo_t` and lacks the DAC capabilities required to read the store reliably; the role-switch surface is documented in [staff_u and sudo role transitions](../foundation/sudo-roles.md). The probe exits `0` on completion regardless of observed state and `2` only on missing tooling (`flatpak`, `xdg-desktop-portal` package not installed, or `systemctl --user` not addressable in the current connection mode).

### Verify

```bash
bash ansible/roles/topic_flatpak_portal_cache/files/verify.sh
```

The verify script compares observed state against a hardcoded expected set and exits `0` on a clean match, `1` on drift, and `2` on invocation error. The expected set covers three end-state facts:

| Property | Expected value |
|---|---|
| `xdg-document-portal.service` user-systemd state | `active` |
| Per-application FUSE-by-app token count under `/run/user/${uid}/doc/by-app/<appid>/` | `0` for every `<appid>` |
| `flatpak documents list` data-row count | `0` |

The persistent-class count is reported as a necessary-but-not-sufficient signal of cache flush; the authoritative signal is the FUSE-by-app per-application token count, because the FUSE path captures the transient class that `flatpak documents list` does not surface. The verify reports the per-application token count as a per-`<appid>` line in its output to make drift attribution unambiguous. The verify is post-reset-applicable — it asserts the post-reset state and is meaningfully a no-op when invoked pre-reset on a host where the cache has not yet been flushed; in that case it exits `0` with an informational note rather than `1`. Liveness probes are not part of the canonical Soll/Ist comparison; the user-systemd `active` state already asserts a live main process. Where any liveness inspection is required elsewhere, the verify uses the `[[ -d /proc/${pid} ]]` form rather than `kill -0`, because cross-user `kill -0` from a non-privileged context against a foreign-uid PID returns `EPERM` rather than `ESRCH` and would misreport a live process as dead. The verify does not exercise any Flatpak-application launch trigger; a host where the operator never re-launches an application post-reset will continue to verify clean indefinitely.

### Cache-state posture

The cache-state posture has three parts.

**Pre-reset state** on a host where the operator has just issued an upstream sandbox-tightening `flatpak override` against an application that previously consumed portal-mediated file access: `flatpak documents list` may report zero or more persistent rows (depending on whether the application historically called `Add(persistent=true)`), and the FUSE path `/run/user/${uid}/doc/by-app/<appid>/` typically contains one or more token subdirectories — at least the transient tokens from the application's most recent run, plus any persistent tokens. The two counts are independent: an operator may observe `flatpak documents list` empty but `by-app/<appid>/` non-empty (transient-only), the reverse (persistent-only — rare in practice for a recently-active application), or both non-empty. Each non-empty token subdirectory under `by-app/<appid>/` represents a host file the application can still read despite the override.

**Post-reset state** immediately after `systemctl --user restart xdg-document-portal.service`: `flatpak documents list` returns the no-document marker (zero data rows); the FUSE path `/run/user/${uid}/doc/by-app/` either does not exist (the portal-service has not been re-spawned yet) or exists empty. Both counts are zero. The application-side effect: any file handle the application held against a token path is invalidated; the next read on a stale token returns an I/O error from the FUSE layer.

**Drift signals on an applied host:** any per-application token count above zero under `/run/user/${uid}/doc/by-app/<appid>/` immediately post-reset indicates the reset did not flush the cache (typical root cause: an out-of-sequence reset call that ran before the upstream override finished writing the override store, or a portal-service that was re-started while a Flatpak application was actively requesting a fresh token mid-restart). A surge of new token counts arriving at later inspection times is **not** drift caused by this topic and is investigated independently — the typical cause is that the operator re-launched a Flatpak application post-reset and the application requested fresh tokens under the new sandbox manifest, which is the intended new authorization scope, not drift.

The role's modify stage is **not** strictly idempotent in the Ansible-`--check`-reports-zero-changes sense: `ansible.builtin.systemd_service` with `state: restarted` re-issues the user-bus restart on every Ansible run. This is a deliberate design choice for this topic, because the role is post-override-applicable: an operator triggers the role manually (or via an orchestrating playbook) immediately after issuing an upstream `flatpak override` push, and the restart action is the role's primary deliverable. The role does not include a guard that skips the restart on a host where the cache was already empty, because the cost of an extra portal-service restart is negligible (the service re-spawns on the next D-Bus method call), and the alternative — a pre-restart probe of the FUSE path — would produce a TOCTOU window where a Flatpak application running in parallel could create a fresh token between the probe and the skip-decision. On a correctly applied host, `--check` reports the user-systemd restart task as a change. Stated as a claim, not a guarantee.

Recovery: the topic ships **no** rollback verb. The reset action is itself a recovery primitive — re-running the role at any later time re-flushes the cache to the same end-state. There is no "undo" semantics to define, because the role does not introduce any persistent state. Boot-failure risk for this topic is structurally zero: the reset action runs against a per-user user-systemd-managed unit that is not active during the system boot sequence and does not introduce any system-init dependency. The worst-case post-application symptom is that an operator who restarted the portal-service mid-Flatpak-application-launch sees the application briefly fail to acquire a token; the application typically re-requests on the next user action and the path self-heals.

## Related patterns

This topic does not cross-link any pattern article. The reset reflex flushes a per-user runtime cache held by a user-systemd-managed service whose lifecycle is independent of the system-init pipeline; the reset does not exercise the kernel NoNewPrivileges-transition constraint, the systemd `SystemCallFilter` privilege-drop sequence, the systemd `PrivateMounts` implicit-enable, the systemd `ReadWritePaths` runtime race, the cross-user liveness-probe trap, or any other cross-cutting hardening pattern documented in this tree. The Topic ships no system-wide configuration file, no SELinux module, no systemd drop-in, and no file-label change — the per-user `systemctl --user restart` invocation carries the entire deploy.
